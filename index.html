整合 74,823 筆歷史維修紀錄、17 份技術手冊（1,007 頁）與測試統計。提示詞層約束不得輸出無來源的數字、頁碼與零件位置。

評測刻意不給維修紀錄，因此命中率量到的是「手冊本身夠不夠用」，而不是模型背答案的能力。

台股走勢預測
個人專案

以 anchored walk-forward ＋ 20 日 embargo 驗證的選股模型，GitHub Actions 每交易日自動重訓。結論是負面的，而我把它寫在 README 第一段。

  • 56.2% 準確率，低於「全猜上漲」57.0%
  • 0.498 最近一折 AUC，低於隨機
  • ≈85% 波動度模型前 10% 把握

價格方向：準確率低於多數類基準，最近一折 AUC 低於隨機。加入台股實際交易成本（年化拖累 8.10%）回測後，策略年化 +21~24%，輸給完全不交易的等權買進持有 +29.9%——選股有毛超額報酬，但不夠付手續費。

換一個標籤則得到正面結果。改預測「未來 20 日波動度會不會放大」，前 10% 把握準確率約 85%。為確認這不是均值回歸的免費午餐，我加了一條一行規則當對照組：真實資料上模型五折全勝（85.4% vs 76.3%），而在我刻意注入波動群聚的合成資料上一行規則反而勝出——這反過來驗證了對照組有效。但波動不提供方向，不能當買賣訊號。

一次排錯。三次執行相同程式碼，回測年化在 +21.2%~+24.5% 間跳動，兩個基準卻完全相同。依序排除隨機種子、執行緒浮點歸約、管線本身，最後證實是上游改寫歷史值：252 檔中 50 檔在數分鐘內內容改變。代表選股決策對數值上可忽略的擾動並不穩健，因此所有報酬都以區間呈現。

我是吳明翰，資訊管理背景出身，從伺服器維修做到軟韌體測試，現在主要在做測試資料的自動化。我的習慣是遇到問題先弄清楚根因再動手，數字對不上時會回頭查判定邏輯，而不是把表面結果改對就算了。個性上我算開朗好溝通，在團隊裡常扮演橋樑的角色。工作之外我喜歡閱讀心理學書籍與運動，前者讓我更懂得怎麼跟不同立場的人對話，後者讓我在高壓期間還能維持穩定。

大學專題：第一次完整交付一個東西

大學時我參與一個與自身家庭行業相關的專題，主題是麻油產業的品牌網站規劃與建置。我負責資料與數據的收集整合，並直接與業主溝通需求，把大量雜訊過濾掉，整理成組員能看懂的簡報再進行分工。這是我第一次完整走過「需求訪談、資料整理、網頁設計、成果報告」的流程，也讓我發現自己真正的興趣在於把混亂的資訊整理成可用的東西。

碩士：學會用資料說話

為了補足資料分析能力，我進入高科大資管所。碩士論文以工作要求－資源模式探討遠距工作者的工作績效及其影響因素，從問卷設計、樣本蒐集、信效度檢驗到以 SPSS 與 SmartPLS 驗證研究模型，完整跑過一次量化研究的流程。這段訓練讓我習慣先問「這個數字怎麼算出來的、樣本有沒有被污染」，而不是直接相信報表。課餘我自學 Python 與 scikit-learn，把所學做成股票查詢與走勢預測的個人專案，這是我開始大量寫程式的起點。

RMA 維修：把手弄髒的兩年半

畢業後我進入緯穎 RMA 部門，負責伺服器板卡的 IC 級維修：操作 BGA 機台拆換不良 IC、以 X-ray 檢查錫球與氣泡、用顯微鏡微調 CPU 針腳，並以 Cadence Allegro 查看點位判斷短路風險。我不只把件修好，也會回頭找為什麼修不好：機台參數怎麼調才能讓 Sample 穩定、載具與鋼片規格要提供哪些數據、哪些手法應該寫進 SOP。這兩年半我把維修 WIP 維持在 5% 以下、良率 97%。這段經歷讓我對伺服器硬體有實際手感，後來做測試與 Debug 時，判斷問題落在哪一層會比別人快。

轉任軟韌體測試工程師：從硬體走到系統

碩士畢業後我回到緯穎，轉任軟韌體測試工程師，負責北美雲端客戶兩大平台的伺服器產品測試驗證與異常排除，合計 14 個專案，每天大約處理 5 到 10 件異常。一邊做 BMC 驅動的 bring-up 與 debug；另一邊多半從 OS 端檢查 PCIe、GPU 與 Driver，搭配壓力與效能測試，判斷問題落在網路、PCIe、Driver 還是 FW。測試環境的網路也由我負責，使用 Cisco、Edge-Core、Wedge100/400 設定路由器與交換器。

從自動化平台到 AI：把重複的工作變成系統

我發現部門花了大量時間在人工查資料庫、整理報表，同一份數字每天有人重算一次，因此從零建置了測試工程自動化平台。用 Python 搭配 MS SQL 與 Linux 排程，自動解析站台原始 log、每日新增逾 100 筆測試場次資料，十餘支程式接力執行並具備階段失敗偵測，產出五個報表頁並以 Teams 推播日報。導入前每天要專人花約一小時整理報表，現在只需約五分鐘確認，每個月省下約 20 個工時。

這個專案讓我學最多的是資料正確性與變更安全。統計數字怪怪的時候，追下去才發現是判定邏輯的問題，所以我重新設計了場次與 SN 生命週期規則，假邊界從 4,681 降到 569，誤判才真正消失。動正式環境時我一定先乾跑模擬、驗證比對次數，數量不符就整批中止，通過後自動備份並經語法檢查才落地。這套習慣讓主機連續運作 105 天、每日體檢 0 錯誤。

最想談的一件事：怎麼知道 AI 答得準

資料乾淨之後，我做了地端 AI 問答系統：接上 74,823 筆維修紀錄與 17 份技術手冊，讓同事直接問「這個板子這個症狀怎麼修」。但系統上線後我面對的問題是——它看起來答得不錯，但「不錯」是幾分？

所以我做了自動評測機制。系統自動列舉「機種 × 症狀」組合出題，作答時刻意只給手冊、不給維修紀錄，答完再拿真實紀錄自動比對判級。不給答案，才量得出它真的會不會。目前已判 9.9 萬題，可比對的 7,029 題命中率 65%。

收穫超出預期的是答錯那一批。第一題它就把「測不出問題」猜成記憶體故障，而真實紀錄是九千多筆裡只有五筆需要往下修，正解是重測不拆。這類落差不只是模型錯，更是手冊與現場實務不一致的地方，反而成了技術文件該更新的清單。我後來也靠評測結果回溯發現手冊索引的比對缺陷，一次修正了約 9,200 筆錯誤回答。

我在設計上最堅持的是不准編。回答固定三段、各段材料互相隔離，沒有來源的數字、頁碼與零件位置一律不准出現。我寧願它回答「資料不足」，也不要它講一個看起來合理但不存在的零件位置——在維修現場，一個編造的料號會讓人白拆一片板子。

跨部門協調

我參與過兩次部門遷移，擔任現場核心協調角色，負責跨單位溝通、人力調度與網路環境建置，並即時處理突發狀況。這類工作技術含量不一定最高，但很吃溝通與事前規劃，也是我相對擅長的部分。

個人專案與下一步

工作之外我持續寫自己的專案。台股走勢預測那個讓我學到最多的不是建模，是評估。我用 anchored walk-forward 加 embargo 做驗證，結果誠實告訴我最近一折 AUC 只有 0.498、準確率 56.2% 還輸給「全猜上漲」的 57.0%；加入實際交易成本回測後，策略甚至輸給完全不交易。更有意思的是過程中我自己提過的兩個假設都被實驗推翻——我一度認定主導變數是市場層級的回撤、模型學到的是市場擇時，但特徵消融顯示那三個特徵的邊際貢獻只有 +0.015，推論不成立。我把推翻的過程也留在報告裡。改預測波動度後倒是得到正面結果（前 10% 把握約 85%），而且先用一條一行規則當對照組確認它不是免費午餐。能證明模型沒有 edge，跟做出 edge 一樣需要正確的驗證設計。

接下來我希望轉任 AI 應用工程師，專注在企業內部的 LLM 導入、RAG 系統與模型評測。我不是從模型研究進入 AI，而是從一個很具體的現場問題開始，這讓我對「怎麼讓語言模型在有事實責任的場合被信任」特別有感。目前正在補強語意檢索（向量嵌入與重排序），把現有的字面檢索經驗銜接到完整的 RAG 技術棧。
